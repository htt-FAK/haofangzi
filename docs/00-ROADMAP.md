# ROADMAP · 后续迭代（本期不实现的点子都在这里，避免范围蔓延）

宪法第三条要求：任何超范围想法先落到本文件，不进本期 spec。

## v1.1 展示与体验
- CAD/DXF 图纸导入 + 墙线自动重建几何（当前靠人工录入 `hf_room`）
- 真实日照模拟（逐时太阳高度角 × 遮挡体 → 日照时长）替代 `LIGHT_floor_occlusion` 简化式
- VR（WebXR）样板间漫游；家具摆放与碰撞检查；移动端 WebGL 优化与降级策略
- 720° 全景由人工素材 → AI 单图生全景（图生图模型）

## v1.2 评估能力
- 引入历史成交价与板块指标，做"性价比"回归修正（仍保留规则分为主，模型分为参考层）
- 无障碍/适老化维度（走廊净宽回转直径、卫浴高差）——契合"好房子"政策导向
- 户型缺陷知识库（暗卫、长走道、开门见厕、西晒强反射）与自动标注
- 权重由用户 pairwise 比较反推（AHP 一致性检验），替代固定人群模板

## v1.3 交易与协作
- 意向单转定金/合同（对接真实支付需与指导老师确认合规口径）
- 家庭多人协作选房：共享收藏池、评论与投票（当前仅分享链接只读）
- 顾问端小程序、到访电子签到、带看路线规划
- 与售楼系统销控表双向同步（需企业侧接口，课程外条件）

## v2.0 平台化
- 多城市/多楼盘租户化（SaaS 化：楼盘管理员自助维护规则集与房源）
- 规则市场：发布自定义评估模板、他人可订阅与评分对照
- 政策合规检查器（《住宅项目规范》条文结构化，逐条出具合规报告）
- 语音/数字人带看讲解（复用全景视点数据）

## 已知取舍与理由（答辩高频追问，先记在此）
| 问题 | 回答口径 |
| --- | --- |
| 为什么不用 Drools/规则引擎库 | 自研 JSON DSL 才能把"AI 生成规则 + 人工审阅"闭环讲清楚，且依赖可控、学生可完全解释（宪法第六条） |
| 为什么评分不直接用大模型 | 不可解释、不可复现，违反 NFR-11；AI 只写规则与解读，分数永远由确定性引擎算出 |
| 为什么不用 MQ 做锁超时 | 单体 + 定时扫描满足 3-4 人课程项目，队列会引入部署复杂度与故障面；已记录 Redis/DB 演进路径 |
| 数据为什么是模拟的 | 无真实销控开放接口；已用真实政策指标口径构造 20 套贴近肇庆"好房子"样本，`seed-data.sql` 可整体替换 |
